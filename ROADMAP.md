# ROADMAP.md — Implementation Tracker

## Purpose

Track every phase, feature, page, reusable component, layout, and API integration required to build CosDash OS, with current status and dependencies. This is a living document — update status inline as work completes. Do not remove completed items; mark them `Complete` instead.

> **Provenance note:** The source material (`COSMADEOS.txt`) references "Volume 5 — Master Execution Roadmap (10 Lovable implementation phases...)" as a planned future volume, but its actual phase content was never authored — only the name and one-line scope description exist in the source. The 10-phase breakdown below is therefore **proposed by the implementation team** (this document), derived from the documented architecture, the two logged ADRs, and the "App Shell before Dashboard" sequencing decision — not a transcription of a pre-existing decided plan. Treat phase order and boundaries as a proposal to confirm/adjust, not settled fact, and record any change to it in [DECISIONS.md](DECISIONS.md).

## How to Read This Document

- **Status values:** `Not Started` · `In Progress` · `Blocked` · `Complete`
- Every feature must clear the [Enterprise Quality Checklist](11%20UX%20System/enterprise-quality-checklist.md) before being marked `Complete` — see [SKILLS.md](SKILLS.md) and the "Never Skip" list this project now operates under (loading/empty/error/permission/success states, responsive layouts, keyboard nav, accessibility, animations, dark mode, hover/focus states, mobile/tablet/desktop layouts).
- Each phase must finish completely (including polish, responsive, accessibility, testing) before the next phase begins — no jumping ahead.

## Stack Decision (resolved)

Frontend: **Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui**. Note: this shadcn/ui installation uses the **Base UI** primitive style (`@base-ui/react`), not Radix — composition uses a `render={<Element/>}` prop, not `asChild`. Codebase lives in `web/`. Auth: **NextAuth.js / Auth.js v5** (ADR-005), Credentials provider against a mock user table until Implementation Volume 2 exists. Backend/data layer: still none otherwise (Volumes 2–3 unauthored) — every other feature still works against mock/local data; see `web/src/lib/mock-users.ts` and `mock-session.ts`.

**Route structure:** `web/src/app/(app)/` holds every authenticated workspace route, wrapped by `(app)/layout.tsx` (fetches the real session, redirects to `/login` if absent, mounts `AppShell`). `web/src/app/login/` sits outside that group so signed-out users don't see the nav/sidebar. `web/src/proxy.ts` (Next.js 16's renamed middleware convention) enforces the redirect at the edge before any page code runs.

## Global Blocker

None currently blocking Phase 1 continuation. Volumes 2–4 remain unauthored, so no feature requiring real persistence, auth, or an API can proceed past mock data — flag this again when Phase 1 reaches Authentication.

**Retroactive correction (found during Phase 6 Playbooks verification, see below):** the "filter selection updating a real chip" claim above was itself a false positive. `FilterTriggerButton` (`advanced-filter.tsx`) never accepted or forwarded `...props`, so when `PopoverTrigger`'s `render` prop tried to inject its open/close handlers and `ref` onto it, they were silently dropped — the Filters button rendered but never actually opened the popover, on this dev harness or any page built on it since. Every verification pass this whole session checked for the filter field's *label text* (e.g. "Industry", "Status") appearing on the page, and every one of those labels happened to coincide with text already present elsewhere (a table column header, mostly), producing a false "it opened" reading every time. **Critical bug found and fixed during this slice — affects every page built since Phase 3, not just this one:** while verifying Playbooks' Filters button, clicking it appeared to do nothing (no visible popover). In every case, the label text happened to coincide with something already visible elsewhere on the page (a table column header, mostly), producing a false "it opened" reading every single time.

**Fixed** by making `FilterTriggerButton` accept and spread `...props: ComponentProps<typeof Button>` onto its `Button`, matching the same forwarding convention `Button` itself already uses for `ButtonPrimitive`. ## Cross-Cutting Bug: Mobile Sidebar Covering the Header

**Found and fixed 2026-07-26.** Clicking the mobile-only `SidebarTrigger` ("Toggle Sidebar," shown in the `md:hidden` row of `AppShell`) opened a full-height (`inset-y-0`/`h-full`, `z-50`) `Sheet` drawer that rendered above the sticky `TopNavBar` (`z-40`) and started at the very top of the viewport — visually covering the header entirely while open, contrary to the platform's Universal Page Anatomy (Top Navigation is always visible above the Workspace Sidebar).

**Root cause:** `Sidebar`'s mobile branch (`web/src/components/ui/sidebar.tsx`) passed no positioning override to `SheetContent`, so it inherited the base `Sheet` component's `data-[side=left]:inset-y-0`/`h-full` — correct for a generic full-screen drawer, wrong for this app's two-tier header-then-sidebar layout. The equivalent desktop-sidebar fix (`top-14`/`h-[calc(100svh-3.5rem)]`, offsetting below the header) already existed in `workspace-sidebar.tsx`, but nothing analogous existed for the mobile `Sheet` variant.

**Fix:** added `data-[side=left]:top-14 data-[side=left]:h-[calc(100svh-3.5rem)]` (and the `[side=right]` equivalent) to the mobile `SheetContent`'s className. The `data-[side=*]` prefix is required, not cosmetic — the base classes' own `data-[side=left]:inset-y-0`/`h-full` carry higher CSS specificity (attribute-selector-scoped) than a plain unprefixed utility, so an earlier attempt using bare `top-14`/`h-[...]` silently lost the cascade and had no visible effect.

Verified live via direct DOM geometry checks (screenshots aren't available in this environment) at both a mobile viewport (375px, Sheet-based sidebar) and a desktop viewport (1280px, persistent sidebar): in both cases the sidebar's `top` now exactly matches the header's `bottom` (56px), with no overlap.

### Accessibility audit findings

**A real, platform-wide bug found and fixed:** every colored status badge (the `STATUS_TONE`-record pattern used ~50 times across Sales/Finance/Operations/Training/HR) failed WCAG 2.2 AA's 4.5:1 contrast requirement in light mode — `text-destructive` badges measured 4.01:1, `text-emerald-600` 3.34:1, `text-amber-600` 2.96:1. `text-destructive` also failed on plain white (2.93:1), affecting the repeated "Delete permanently" link pattern. A separate, narrower failure: the neutral/default badge pattern (`bg-muted text-muted-foreground`, 19 files) measured 4.37:1 against its own background. Root-caused and fixed at the token/pattern level (not per-file) — see **ADR-008** in [DECISIONS.md](DECISIONS.md) for full detail, the exact values changed, and the live-verified post-fix ratios (all now 4.66–5.57:1 in the colored badges, >6:1 in neutral badges). Dark mode already passed everywhere (6–10:1) and required no change.

**Verified already correct, no changes needed:**
- The mobile `SidebarTrigger` ("Toggle Sidebar") uses a proper `<span class="sr-only">Toggle Sidebar</span>` accessible name behind its icon — confirmed via direct DOM inspection (a fully accurate screen-reader-friendly pattern, even though this session's browser-automation tool's own accessibility-tree extraction doesn't surface `sr-only` text, which initially looked like a false-positive bug).
- Checkbox components' underlying native `<input>` elements are correctly `tabindex="-1"` and `aria-hidden="true"`, so bulk-select tables don't create confusing empty stops in the keyboard tab order.
- The Kanban board (`KanbanBoard`/dnd-kit, Applicants pipeline) is genuinely keyboard-accessible: draggable cards are focusable with meaningful accessible names (derived from card text content), `aria-describedby` points to real dnd-kit-authored instructions ("To pick up a draggable item, press the space bar..."), and a live region (`aria-live="assertive"`) exists for drag-state announcements — validates the original choice of dnd-kit (Task #18) specifically for its accessible drag-and-drop support.

**Not yet audited:** full keyboard-only click-through of every page; screen-reader testing with an actual AT (NVDA/VoiceOver) rather than DOM/ARIA-tree inspection; high-zoom behavior; every one of the ~96 routes individually (only the shared components + representative archetypes above were checked).

**Reduced motion — real gap found and fixed (2026-08-15):** `accessibility-performance-standards.md` explicitly requires "Every interaction must be usable with... reduced motion preferences," but a codebase-wide search found zero `prefers-reduced-motion` handling anywhere except inside two third-party library styles (`tw-animate-css`'s `.shimmer`, Sonner's toast transitions) — every Base UI Dialog/Sheet/Popover open-close animation, hover/focus transition, and dnd-kit drag motion ignored the OS-level setting entirely. Fixed at the global CSS layer (`web/src/app/globals.css`, consistent with ADR-008's precedent of root-causing at the token/pattern level): a `@media (prefers-reduced-motion: reduce)` block collapses all `animation-duration`/`transition-duration`/`scroll-behavior` to near-zero platform-wide. Verified the rule compiles into the served stylesheet (confirmed via live `document.styleSheets` inspection) and coexists correctly alongside the two pre-existing library-level rules. Clean `tsc --noEmit` after the change.

### Responsive audit findings

**Original pass:** checked at 320px, 375px, 768px, 1024px, and desktop width across the Dashboard, Vendors list, a Vendor detail page (Universal Object Layout), the Applicants Kanban board, and the Knowledge Editor New Page (a multi-column form): no page-level horizontal overflow (`document.documentElement.scrollWidth` matches viewport width) at any breakpoint on any of the five. **Extended pass (2026-08-15):** swept the remaining 9 breakpoints in the required matrix (1600, 1440, 1366, 1280, 820, 540, 430, 390, 360) on the Vendors list (table archetype, highest overflow risk) — no page-level horizontal overflow at any of the 9. Visually confirmed at 360px: the table's `Category` column correctly scrolls horizontally within its own bounded container (the same deliberate, contained pattern as the workspace switcher — not a bug), and the pagination row's text is intact and un-truncated in the DOM (a floating overlay in the screenshot briefly appeared to cover it, but that overlay is the browser-automation tooling's own chrome, not an app element).

Attempted to check Dialog/Sheet fit-within-viewport at 320px (Create Vendor sheet): confirmed functionally — the sheet opens, and its form input is present, focusable, and accepts text entry correctly at 320px. Could **not** get a reliable visual/animation-settled position reading this session: the browser automation pane was not compositing frames (`the Browser pane is not displayed, so the page is not compositing frames` — the same non-compositing-environment limitation already logged for Dialog/Sheet exit animations), which appears to stall Base UI's CSS-transition-completion detection and left the sheet mid-enter-animation indefinitely (a `translate-x` offset matching exactly the enter-transition's `2.5rem` constant, persisting well past the transition's 200ms duration). **Still not yet audited:** Table-heavy pages at narrow widths beyond the horizontal-overflow/inner-scroll check (per-page visual legibility of specific cell content across all list pages, not just the Vendors sample); the full 9-breakpoint sweep on pages other than Vendors (Dashboard, Vendor detail, Kanban, Knowledge Editor were only confirmed at the original 5 breakpoints).

### Performance audit findings — Pagination rollout

**A real, platform-wide gap found and fixed:** no `Pagination` component existed anywhere in the codebase, despite CLAUDE.md requiring "Pagination or Infinite Scroll" on every list page and `accessibility-performance-standards.md` requiring large datasets use "virtualization, pagination, or progressive loading" — every list page rendered its full filtered array unbounded. Built `web/src/components/ui/pagination.tsx`: a `usePagination(items, pageSize)` hook (slicing, page-size selection from `[10, 25, 50, 100]`, auto-clamping the current page back into range when a search/filter shrinks the result set) plus a `Pagination` control (Previous/Next, page range, rows-per-page selector, renders nothing for an empty list).

Deliberately **not** retrofitted: the genuinely public `/careers` page (a marketing-style content page outside the `(app)` route group per ADR-007, not an internal operational list view — CLAUDE.md's Universal Toolbar/pagination requirement targets enterprise list pages, not public content feeds); Reports/Progress/Budget Planning-style analytics pages (small, fixed-size computed summary tables, not paginated entity browsing).
