# MEMORY.md — Durable Project Knowledge Log

Continuously updated. Records architectural decisions, naming conventions, preferred patterns, rejected approaches, recurring preferences, technical standards, UI conventions, business rules, and lessons learned. Does **not** store temporary implementation details — see task tracking for that.

## Architectural Decisions
- The platform is workspace-based, not module-based; every department is a full workspace (dashboard + objects + analytics + documents + AI + automation + settings). Source: Implementation Series Vol. 1.
- Every business object uses the Universal Object Layout (same tab set: Overview, Activity, Relationships, Documents, Knowledge, Tasks, Timeline, Analytics, AI, History, Settings). Never a cramped modal for a major entity.
- Maximum navigation depth is 4 levels (Workspace → Section → Object → Details).
- App Shell must be fully specified before the Dashboard is designed (see [DECISIONS.md](DECISIONS.md) ADR-001).
- **Functionality-first standard (ADR-006, 2026-07-13):** a page that only displays data is incomplete unless read-only is a deliberate decision. Every entity needs its full CRUD lifecycle (incl. Duplicate/Restore/Permanent Delete/Version History/Comments), every list page needs Quick Preview + Context Menu on top of the existing Universal Toolbar, every detail page needs a Quick Actions panel, and every workspace needs a representative real-world action set (see CLAUDE.md → "Functionality-First Implementation Rules" for the full checklist and per-department examples). **Retrofit fully complete as of 2026-07-14** (all 9 pre-ADR-006 entities across Sales and HR); Marketing (Phase 7) and the remainder of HR (Phase 5) were subsequently built to this bar from day one. See ROADMAP.md Phase 5/6/7 sections for full detail.
- **Genuinely public pages live outside `(app)` (ADR-007, 2026-07-26):** any route that must work for an unauthenticated visitor (e.g. `/careers`) goes at `src/app/<name>/page.tsx`, a sibling of `(app)`/`login`, never inside `(app)` with a bypass. No `middleware.ts`/`proxy.ts` exists in this project — the only auth gate is the `(app)` layout's own `auth()` redirect, which a sibling route structurally never passes through. Confirm via production build output: a genuinely public route renders as a static `○`, not a server-rendered `ƒ`.

## Naming Conventions
- Top-level global navigation items are business functions/workspaces (`Sales`, `Finance`, `Knowledge Base`), never generic page names.
- Object detail tabs are standardized platform-wide; departments do not get to rename them.
- Documentation folders use `NN Folder Name` numbering exactly as in [README.md](README.md).

## Preferred Patterns
- Drawers for viewing/editing/reading/comments/preview/history/relationships/timeline. Modals **only** for destructive/dangerous confirmations (delete, archive, approval, reject, publish, password/auth). New pages for complex authoring work (Knowledge Editor, Campaign Builder, Research Workspace, Workflow Builder, Report Designer, Document Editor).
- Undo-first for destructive actions: Archive → Undo → Delete Permanently, wherever safe.
- Saved, personalized views per user (private by default, shareable).
- AI is always a contextual panel, never a hidden chat window; every AI action is labeled.

## Rejected / Corrected Approaches
- **Dashboard-centric department landing pages** — rejected. The design-structure teardown explicitly corrects this: "Cosmade OS currently looks too dashboard-heavy... every workspace should primarily become a working environment." Dashboards are overview pages; the default landing experience for daily work is a productivity surface (table, pipeline, editor), not KPI cards. See [11 UX System/design-system-teardown.md](11%20UX%20System/design-system-teardown.md).
- **Saturated color / heavy-shadow active states** — rejected in favor of soft/subtle active states (light gray tab background, soft lavender selected sidebar item), matching the reference application's low-saturation, high-whitespace visual language.

## Recurring Preferences
- Generous white space and medium information density over compressed, crowded layouts.
- Monochrome outline icons, consistent weight, small size.
- Table-first working pages over card/widget-heavy pages for operational (non-dashboard) screens.

## Technical Standards — Implementation (web/)
- Stack: Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui, codebase in `web/`.
- **This shadcn/ui installation uses Base UI (`@base-ui/react`), not Radix.** Composition pattern is `render={<Element/>}`, never `asChild` — passing `asChild` silently fails (renders as a stray DOM attribute and produces nested `<button>` hydration errors) instead of erroring at compile time. Every Trigger-style component (PopoverTrigger, DropdownMenuTrigger, TooltipTrigger, SidebarMenuButton, etc.) needs `render={<Button .../>}` with the human-readable content left as the Trigger's own children — see `web/src/components/shell/profile-menu.tsx` for the canonical pattern.
- Base UI Select's `onValueChange` is typed `(value: string | null, ...) => void` — always guard against `null` before calling a setState/router function that expects a bare `string`.
- If Turbopack/Next dev server shows a hydration error that doesn't match current source (e.g. after fixing the exact bug it's complaining about), clear `web/.next` and restart — seen a stale-cache false positive during this session.
- No backend/auth provider decided yet — `web/src/lib/mock-session.ts` is a deliberate temporary stub, not a pattern to extend.
- Base UI's `Menu.GroupLabel` (shadcn's `DropdownMenuLabel`) throws "MenuGroupContext is missing" unless wrapped in `Menu.Group` (`DropdownMenuGroup`) — required even for a single label with no actual grouped items. This bug was latent through all of Phase 1 because the profile dropdown was never actually clicked open during verification, only screenshotted closed.
- **Lesson:** static screenshots aren't enough to verify a component — popovers/dropdowns/dialogs only mount their content on open, so verification must actually click them open, not just confirm the page loads.
- Dev-only internal pages (design-system reference, etc.) that render interactive demo handlers must be Client Components (`"use client"`) — Next.js App Router Server Components cannot pass function props to Client Components (not serializable across the RSC boundary).
- Never delete `.next` while the dev server is still running — corrupts its on-disk manifests. Always stop the server first, then clear the cache, then restart.
- Auth: NextAuth.js v5 (`web/src/auth.ts`), Credentials provider against `web/src/lib/mock-users.ts` (ADR-005). Real user database still doesn't exist (Volume 2 unauthored) — only `authorizeUser()` needs to change when it does; session/route-protection plumbing (`web/src/proxy.ts`, `(app)/layout.tsx`) stays the same.
- Authenticated routes live under `web/src/app/(app)/`; `/login` is a sibling outside that group specifically so it renders without the App Shell. Any new top-level workspace route goes inside `(app)/`, not next to it.
- Next.js 16 renamed the `middleware.ts` convention to `proxy.ts` (same export shape) — use `proxy.ts`, `middleware.ts` now prints a deprecation warning at build time.
- NextAuth v5's JWT type augmentation must target `@auth/core/jwt` (not just `next-auth/jwt`) or custom JWT fields silently type as `{}` — see `web/src/types/next-auth.d.ts`.
- Never import `web/src/lib/mock-users.ts` (pulls in bcryptjs) from a Client Component — it's server-only (used by `auth.ts`). The login page's demo-account display uses the separate client-safe `web/src/lib/demo-accounts.ts`.
- Base UI's `Select.Value` does NOT auto-derive a label from the matched `Select.Item` the way Radix does — it renders the raw `value` unless you pass a render-function as its children (`<SelectValue>{(value) => lookupLabel(value)}</SelectValue>`) or use object-shaped `{value, label}` items. Found live in `advanced-filter.tsx` — the department filter showed "engineering" instead of "Engineering" until fixed.
- The Phase 3 Universal Object Layout components (`object-header.tsx`, `object-page.tsx`, `object-tabs.tsx`, `page-toolbar.tsx`, `advanced-filter.tsx`, `wizard-shell.tsx`, `record-status-banner.tsx`, `sync-status-banner.tsx`, `metric-card.tsx`) are the shared framework every future department object page (Phase 5+) builds on — never build a bespoke per-department header/tab/toolbar layout.
- **Mock data must be a real shared store (`useSyncExternalStore`), never per-page `useState`.** Found live: the Employee Profile's Archive action showed a success toast but the separate Directory page (local `useState` copy of the same seed array) didn't reflect it — a real Confidence-principle violation, not a demo nitpick. Fixed once in `web/src/lib/mock-data/employees.ts`; every future department's mock dataset (Sales leads, Finance invoices, etc.) should follow the same `subscribe`/`getSnapshot`/mutator-function pattern from day one.
- `PageToolbar` takes a `filters` slot (a fully-built `<AdvancedFilter trigger={<FilterTriggerButton count={...}/>} .../>` element), not an `onFiltersClick` callback — the two don't compose on their own. Use `countActiveFilters()` from `advanced-filter.tsx` to compute the badge count.
- Next.js won't allow a workspace's bare `page.tsx` (e.g. `/hr/page.tsx`) alongside that workspace's `[[...slug]]` optional catch-all — convert the catch-all to a required `[...slug]` once the bare route gets real content (redirect or landing page). Every future department will hit this the moment its landing page is built.
- Client-side mutable module state (the mock data stores) resets on a hard page reload/`window.location.href` navigation — expected, since there's no persistence layer yet. Don't mistake this for a bug; verify cross-page reactivity via real client-side navigation (`<Link>`, `router.push`, or browser back/forward), not `window.location.href`.
- Every form field needs an explicit `id`/`htmlFor` pair — a custom `Field` wrapper that renders `<Label>` as a sibling (not wrapping) the control has no programmatic association by default. Verify with an accessibility snapshot (accessible name should match the label text, e.g. `textbox: "Full name"`), not just a visual screenshot.
- Base UI's `Select` keeps a closed dropdown's `[role="option"]` elements mounted in the DOM (not removed) — querying `[role="option"]` generically when a page has multiple selects is ambiguous and will grab the wrong one. Target by option text instead when testing/automating.
- Multi-step forms (WizardShell-based) should back Save Draft/Exit with real `localStorage` persistence and load it on mount — the "Resume Later" and "your progress is kept as a draft" promises in the spec are only honest if this is real, not decorative.
- `@dnd-kit`'s `DndContext` needs a stable, caller-supplied `id` prop or its auto-generated `aria-describedby` id will differ between SSR and client hydration — a genuine Next.js hydration mismatch, not a false positive. See `web/src/components/ui/kanban-board.tsx`.
- Every drag-and-drop surface (Kanban, etc.) must ship a non-drag fallback (e.g. a "Move to…" dropdown per card) — screen reader and some keyboard users can't complete a drag gesture even with a keyboard sensor configured. This is the pattern to copy for every future Board View instance.
- Synthetic `PointerEvent`/`dispatchEvent` sequences don't reliably trigger pointer-capture-based DnD libraries like dnd-kit — confirmed here (the sensor visibly picked up the drag per its own screen-reader announcement, but never completed a drop). Don't treat a failed synthetic-drag test as proof of a bug; verify the underlying move logic through an accessible alternate path instead, and flag real pointer-drag as needing human verification.
- **This automated browser tool does not fire `requestAnimationFrame` callbacks at all** (confirmed directly: a bare rAF loop hangs indefinitely). Base UI's `Tabs.Panel` (and likely other Base UI components with exit animations) waits on an rAF-scheduled `getAnimations()` check to know when it's safe to unmount an inactive panel — since rAF never fires here, switching tabs via this tool makes the previous panel appear to stay stuck mounted forever (both panels visible), which looks exactly like a real "tabs don't switch" bug but isn't one. Before concluding a Base UI transition/animation-driven behavior is broken, set `globalThis.BASE_UI_ANIMATIONS_DISABLED = true` in the page (bypasses Base UI's rAF/animation-completion path entirely) and retest — confirmed this resolves tab-switching correctly with zero code changes needed, proving the app code was fine and the tool's rAF suppression was the entire cause. Apply this flag proactively before verifying any tabbed/animated Base UI surface (Tabs, Popover, Dialog, Select) going forward, the same way the dnd-kit pointer-capture limitation is treated as a known tool gap, not an app bug.
- Mock entities should reference each other by id (`Applicant.jobListingId`, `Employee.managerId`-equivalent), never duplicate a related entity's display value as a free-text field — the free-text version can't be kept in sync and can't derive live counts/rollups. Presentational components (e.g. `ApplicantCard`) take the *resolved* value as a prop rather than importing the other entity's store directly, keeping components decoupled from which page does the lookup.
- File-upload features should use the real browser File API (`<input type="file">` + a real `File`/`Blob`), never a fake button — it costs nothing extra and lets Download/size/name all be genuinely correct instead of hardcoded. Verify by synthesizing a real `File` + `DataTransfer` and dispatching a real `change` event (works reliably, unlike synthetic PointerEvents for drag-and-drop).
- `useSession()` from `next-auth/react` is available in any page under `(app)/` (wrapped by `AuthSessionProvider` in `(app)/layout.tsx`) — use it to resolve "current user" fields (e.g. "uploaded by") instead of hardcoding or re-deriving from the mock user table.
- When a testing selector is ambiguous (e.g. a CSS class shared by more than one input on the page), `preview_fill`/`querySelector` can silently fill the wrong element. Scope selectors precisely (e.g. `tbody tr input`, or confirm via `document.activeElement` first) rather than trusting a generic class selector — confirmed this cost a false "bug" reading during Team Documents verification that turned out to be my own selector mistake, not app code.
- Confirmed: `KanbanBoard` genuinely generalizes across departments with zero component changes (HR Applicants → Sales Leads, different data shape and stage set, just a different `id` prop) — and the "convert catch-all from optional to required once a workspace's bare landing page exists" routing fix is a real, repeatable pattern every department will hit once it gets a landing page, not a one-off HR quirk.
- Referential-integrity pattern now proven a fifth time (`Applicant.jobListingId`, `Lead.ownerId`, `Lead.companyId`, `Contact.companyId`, `Meeting.contactId`/`Meeting.ownerId`) — treat it as settled: any new relationship between two mock entities is an id reference resolved via a lookup `Map`/`getXById` in the page, never a duplicated free-text field, and the presentational card/row component takes the resolved display value as a prop rather than importing the related store itself.
- New variant of that pattern, first seen on Meetings: when an entity's "company" is really "whoever its parent record belongs to" (a meeting's company is really its contact's company), don't store that id directly on the entity — resolve it by hopping through the parent (`getContactById(meeting.contactId).companyId` → `getCompanyById`). Storing it directly would let it go stale if the contact's company ever changed; the two-hop derived lookup can't.
- When starting a brand-new mock store, add its first real mutator (a status-change action, a delete, etc.) up front rather than waiting to hit the `prefer-const` lint error — it's now a predictable, recurring step (Job Listings, Companies, Meetings all needed one), not a special case worth rediscovering each time.
- **Critical, session-wide bug (found and fixed during Playbooks verification): any custom component used as a Base UI `render` prop target (`<PopoverTrigger render={<X/>}/>`, `<DropdownMenuTrigger render={<X/>}/>`, etc.) MUST accept and spread `...props` (and implicitly `ref`) onto the real element it renders, exactly like `button.tsx`'s `Button` does onto `ButtonPrimitive`.** If it destructures only its own named props and drops the rest (as `FilterTriggerButton` did — `{ count }` only, no `...props`), Base UI silently fails to attach the open/close handlers and `ref` it needs to inject: the button renders, looks normal, and does nothing when clicked. No console error, no warning — it just never opens. This had been broken on **every single page's Filters button since Phase 3** (Companies, Contacts, Meetings, Leads, Job Listings, Applicants, the Phase 3 dev harness) without ever being caught. Fixed once in `advanced-filter.tsx`'s `FilterTriggerButton`, which now fixes it everywhere. Before writing any new component intended to be composed via `render={<X/>}`, give it `...props: ComponentProps<typeof Underlying>` and spread it.
- **The verification-methodology flaw that let the above bug hide all session: never confirm a Popover/Menu/Dialog "opened" by checking whether its content's label text appears on the page.** Base UI keeps overlay content mounted in the DOM at all times (hidden via CSS/`data-closed` state, not removed) — so a text check like `innerText.includes('Industry')` returns true whether or not the popup ever actually opened, and worse, gives an even more misleading false positive if that label text happens to also appear elsewhere on the page (e.g. a table column header sharing the filter field's name, which happened on nearly every page this session). The reliable check is DOM state: `document.querySelector('[data-slot="popover-content"]')` existing (or the equivalent slot for the primitive in question) and having `data-open` / not `hidden`, or a computed `display` other than `none`. Re-verify every prior "Filters works" claim in ROADMAP.md with this method before trusting it, not just newly-built pages.
- When a real-world relationship is one-to-many (a company can have several contacts) but an existing entity only models the one-to-one version of it (`Lead.contactName`, one contact per deal), don't overload the existing field — model the many side as its own entity (`Contact`) referencing the same parent id. Confirmed with Contacts: Lagos General Hospital and Kano Teaching Hospital each carry two contacts, which `Lead` alone couldn't represent.
- When a store's mutable `state` variable trips `prefer-const` because no mutator exists yet, the right fix is to add a genuine mutator with real UI (a status-change action, etc.), not to just change `let` to `const` — this has now happened twice (Job Listings' Close/Reopen, Companies' `setCompanyStatus`/"Mark as [Status]") and is the expected response every time it recurs.
- Testing an async popover/dropdown item via `preview_eval`: open-click and item-click must happen inside the **same** `async` eval call with a short `await new Promise(r => setTimeout(r, ...))` between them — splitting them into two separate `preview_eval` calls lets the menu close (React state settles) before the second call can find the item, producing a false "nothing happened" reading.
- **Permanently deleting a record while viewing its own detail page needs a guard, or it flashes a 404.** The page reads the record reactively from the store (`useCompanies().find(...)`); a permanent-delete mutator removes it from that store immediately, re-rendering the page with `company` now `undefined` — which hits the `if (!company) notFound()` branch and throws Next's 404 *before* the `router.push` navigating away has taken effect, since the store update and the render it triggers are synchronous while the navigation is not. Fix: add a local `deleting` boolean, set it `true` in the same handler that calls the delete mutator (before calling it), and check it ahead of `notFound()` (`if (deleting) return null;`). Needed on every entity detail page that supports Permanent Delete — first hit on Company, apply proactively to Contact/Lead/Meeting/Playbook detail pages rather than rediscovering it each time.
- **A plain, unprefixed Tailwind override class does not reliably beat a `data-[attr=value]:`-prefixed base class, even later in the same `cn()`/`twMerge()` call.** Base UI variant utilities like `data-[side=left]:inset-y-0` compile to an attribute-selector rule with higher CSS specificity than a plain `.top-14`; `twMerge` only dedupes within the same variant "bucket," so when the two don't share the same `data-[...]:` prefix, BOTH classes end up in the output and the higher-specificity one wins the cascade regardless of source order — silently defeating the override with no error. Found live fixing the mobile Sidebar's `Sheet` covering the `TopNavBar`: `className="top-14 h-[calc(100svh-3.5rem)]"` had zero effect until rewritten as `"data-[side=left]:top-14 data-[side=left]:h-[calc(100svh-3.5rem)]"` (matching the base component's own variant prefix exactly). Verify a positioning override actually took effect via `getBoundingClientRect()`, not by trusting the className string is present in the DOM.
- **React Compiler's `react-hooks/preserve-manual-memoization` fires as a real lint ERROR (not a warning) when a derived array/object is assigned to a plain `const` and then used inside another hook's dependency array.** The compiler can't prove the plain `const` is stable across renders, so it bails out of optimizing the whole component. Found in the Finance Banking page: `const activeAccounts = accounts.filter(...)` used inside a `useMemo`'s deps array. Fix: wrap every derived array in its own `React.useMemo`, even ones that look trivial — this project's convention (already followed almost everywhere) turned out to be load-bearing, not just a style preference.
- **This browser automation tool cannot take real screenshots** (`computer{action:"screenshot"}` reliably times out — "Browser pane is not displayed, so the page is not compositing frames"). Never rely on a screenshot to verify layout/positioning bugs (overlaps, z-index, sidebar-covers-header, etc.) in this environment — use `getBoundingClientRect()` / computed-style JS checks instead, which work reliably and give an exact, falsifiable answer.
- **A `useEffect` that defaults a form field from `useSession()` must gate on session status, not just truthiness.** `useSession()` resolves asynchronously; a `defaultAuthor = employees.find(e => e.email === session?.user?.email)?.id ?? employees[0]?.id ?? ""` pattern computes the `employees[0]` fallback on the first render (before the session loads), and a `useEffect` with a `!form.authorId` guard fires immediately, "locking in" the wrong default — then never re-fires once the real session resolves, since the guard is already satisfied. Found in the Knowledge Editor's Author field (defaulted to Abby Huang instead of the signed-in Jayden Adefala). Fix: check `useSession()`'s `status === "authenticated"` before computing any session-derived default, so the fallback literally cannot fire before the real value is known.
- **Base UI `Dialog`/`Sheet` exit animations (`data-closed:animate-out`) can leave the DOM node present after `onOpenChange(false)` fires in this browser-automation environment**, because the Browser pane doesn't composite frames (see above) and Base UI removes the node on `animationend`/`transitionend`, which may never fire without real paint. Confirmed via a clean reproduction: the underlying state mutation, toast, and re-render all happened correctly (verified via `document.body.innerText` and the mutated store data), and a completely fresh dev server + fresh navigation showed zero console errors — only the `[role="dialog"]` DOM query kept matching. Treat "dialog still in DOM after clicking its submit button" as inconclusive on its own; verify the actual state change instead (does the mutated data appear? did a toast fire? are there real console errors?) before concluding a Dialog itself is broken.
- **Console-error accumulation across `navigate()` calls in this tool is not reliably per-page** — `read_console_messages` can return errors from many navigations ago that appear to implicate the current page's components by name coincidence (e.g., an error naming `CourseEditSheet` reappeared verbatim on the unrelated `/operations/vendors` page). Confirm any console error is real and current by checking it on a **fresh preview server + fresh navigation** before treating it as a live bug.
- **This browser automation environment's system `prefers-color-scheme` is dark**, and this app's theme provider defaults to "system" — so every page renders in dark mode by default unless explicitly switched. Manually poking `document.documentElement.classList`/`setAttribute('data-theme', ...)` does NOT reliably override this (it gets silently re-asserted, producing a confusing hybrid state where some measurements read light-mode values and others read dark), and neither does `location.reload()`. The only reliable way to force light mode for testing is clicking the real `[aria-label="Toggle theme"]` button and then confirming with `document.documentElement.classList.contains('dark')` before trusting any subsequent color/contrast measurement.
- **Tailwind v4's `getComputedStyle().color`/`.backgroundColor` return `oklch()`/`oklab()`/`lab()` strings, not `rgb()`** — a regex expecting `rgba?(...)` silently fails (matches nothing) on these. Convert reliably by setting the string as `ctx.fillStyle` on a real 1×1 `<canvas>` and reading back `getImageData()` — the browser does the color-space conversion correctly regardless of source format. Don't test a *candidate* Tailwind shade class (e.g. `text-emerald-700`) by injecting it into a detached DOM node unless that exact class string already appears somewhere in the actual source tree — Tailwind's JIT only generates CSS for classes it finds in scanned files, so an untested candidate silently falls back to the inherited/default text color (an unstyled near-black), which looks like a suspiciously perfect contrast ratio but is actually a measurement artifact, not the real color.
- **Every colored status badge platform-wide (`text-{emerald,amber,sky}-600`, `text-destructive`, and the neutral `bg-muted text-muted-foreground` pattern) failed WCAG 2.2 AA contrast in light mode** — found and fixed in the Phase 10 accessibility audit by darkening `--destructive` at the token level in `globals.css` and bulk-replacing `-600`→`-700` platform-wide, per **ADR-008** in [DECISIONS.md](DECISIONS.md). Any new status badge should start from `-700` (or `text-destructive`/`text-foreground/70`), never `-600` — that shade is now a known contrast failure, not a style choice.
- **No `Pagination` component existed anywhere in the codebase until the Phase 10 performance pass**, despite CLAUDE.md requiring it on every list page — every list rendered its full filtered array unbounded. Fixed platform-wide: `web/src/components/ui/pagination.tsx` (`usePagination` hook + `Pagination` control), rolled out to all 29 list surfaces including the three shared list-page renderers (`PolicyDocumentListPage`, `SopListPage`, `KnowledgeBaseListPage`), which each fix multiple routes from one file. Any new list page should use this from the start — `usePagination(filtered)` + render `<Pagination {...pagination} .../>` after the scroll container, and select-all checkboxes should operate on `pagination.pageItems` (current page only), not the full filtered array.
- **A regex-based bulk find/replace across many structurally-similar files works well for 90% of cases but silently mis-fires on structural outliers** — found retrofitting pagination: `sales/meetings/page.tsx`'s row iterator destructured `({ meeting, contact, company, owner })` instead of a single identifier, and `training/departmental/page.tsx` used a `rollup` variable instead of `filtered`, so the generic regex either skipped them (safe) or, in departmental's case, inserted a `<Pagination>` block matching a coincidental `)}\n</div>` pattern without the supporting hook/import (a real bug, caught by `tsc --noEmit`). After any bulk regex edit across many files, grep every target file for the pattern that was *supposed* to disappear (e.g. stale `filtered.map(` alongside a newly-added `usePagination` call) rather than trusting the script's own success/failure report alone — the report only reflects what the regex looked for, not what's actually broken.
- **A card-grid list page can have `selected` state and bulk-action buttons wired up with no checkbox UI on the cards at all** — found and fixed on `/hr/benefits`: `BenefitsPage` defined `selected`/`onClearSelection`/bulk Archive+Delete in `PageToolbar`, but the card grid never rendered a `Checkbox` to actually populate `selected`, making the bulk actions permanently unreachable. Fixed by adding the same per-card `Checkbox` pattern already used correctly elsewhere (Brand Assets, Creative Library, Knowledge/Playbooks cards). Worth a quick grep (`bulkActions=` without a matching `Checkbox` in the same file) on any future card-grid page to catch this class of bug early.
- **A shared component can exist, be well-built, and still be a real gap if nothing in the live app actually renders it.** `SyncStatusBanner` (Offline/Sync Pending) and `ErrorState`/`PermissionDeniedState` all existed since Phase 3 but were only ever referenced from internal `/dev/*` demo pages — a `grep -rl "ComponentName" src/app` that only turns up `/dev/` routes means the Universal State it represents is not actually wired into the product, no matter how complete the component itself looks. Fixed for Offline (real `navigator.onLine` + `online`/`offline` listeners via `web/src/lib/use-online-status.ts`, wired into `AppShell`) and Maintenance (a real `Switch` in the Developer Preview Toolbar, wired into `AppShell` — also the toolbar's first real "Workflow State Switcher" implementation). Left deliberately unwired: Sync Pending (no real pending-change queue exists to report on honestly), Error (no network layer exists to fail; `toast.error()` is the load-bearing equivalent this session already uses), Permission Denied (blocked on the same missing RBAC model as the Security audit).
- **Base UI `Checkbox`/`Switch` put their `id` on the visually-hidden native `<input>` (`tabindex="-1" aria-hidden="true"`), not on the visible clickable root.** `document.getElementById(id).click()` in this automation environment clicks that hidden input and does NOT reliably trigger the component's real toggle logic — the visible root's `data-checked`/`data-unchecked` attribute stays unchanged. Query `[data-slot="switch"]` (or `[data-slot="checkbox"]`) and click *that* instead; verify the click worked via `data-checked`/`data-unchecked` before trusting any subsequent assertion about the toggled state.

## Technical Standards
- Every list/table view carries the full Universal Toolbar: Search, Filters, Saved Views, Sort, Group, Columns, Density, Export, Import, Refresh, Create, Bulk Actions.
- Every screen must define all Universal States: Empty, Loading, Skeleton, Partial, Offline, Sync Pending, Permission Denied, Error, Archived, Deleted, Read Only, Maintenance.
- Responsive testing mandatory at: 1920px+, 1600, 1440, 1366, 1280, 1024, 820, 768, 540, 430, 390, 375, 360, 320px.
- WCAG 2.2 AA accessibility target; keyboard-only, screen-reader, and reduced-motion usable interactions required for everything.

## UI Conventions
- Primary action: top right. Secondary actions: dropdown, never scattered.
- Object header standard: icon, name, status, owner, department, last updated, quick actions, share, favorite, AI summary, health indicator, relationship count, approval status.
- Global keyboard shortcuts: `Ctrl/⌘+K` global search, `N` create new, `/` focus search, `Esc` close drawer, `Ctrl+S` save, arrow keys navigate tables, `Shift+Click` multi-select, `Tab` next field.

## Business Rules
- New modules must integrate with existing navigation/object models; existing workflows must not break; deprecated features get a defined migration period rather than silent removal.
- No feature ships without passing every applicable section of the Enterprise Quality Checklist (UX, Design, Accessibility, Performance, Security, Reliability, Intelligence).

## Lessons Learned
- Providing only a fragment of a much larger conversation (as happened in this documentation pass) is fine as long as gaps are explicitly flagged rather than papered over — this preserves trust in the documentation set. Confirmed as the working method for this project; see [CONTEXT.md](CONTEXT.md) gap notes.
